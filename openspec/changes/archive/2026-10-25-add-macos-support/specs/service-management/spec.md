# Spec Delta

## Purpose

Run the llama-swap service and companion model services as per-user services
under the host's native service manager: systemd on Linux, launchd on macOS.
The service commands must refuse to act on any service definition or process
that `llms` did not generate.

## ADDED Requirements

### Requirement: Service manager selection
The system SHALL choose a service manager with the `service_manager` setting.
Allowed values are `auto`, `systemd` and `launchd`. The default is `auto`, which
SHALL resolve to `launchd` on macOS and `systemd` on Linux. Any other value, or
`auto` on another platform, SHALL be a configuration error.

#### Scenario: Auto-selection on macOS
- **WHEN** `service_manager` is unset and the host is macOS
- **THEN** service commands use launchd

#### Scenario: Auto-selection on Linux
- **WHEN** `service_manager` is unset and the host is Linux
- **THEN** service commands use systemd, exactly as before this change

#### Scenario: Unsupported platform
- **WHEN** `service_manager` is `auto` and the host is neither Linux nor macOS
- **THEN** settings loading fails with an error naming the platform

### Requirement: Logical service names remain compatible
The `unit` setting and each companion's `unit` SHALL accept a logical service
name. For systemd, the name maps to `<name>.service`. For launchd, it maps to a
job label and a `<label>.plist` file. An existing `unit` value ending in
`.service` SHALL still be accepted and SHALL mean the same service on systemd.

#### Scenario: Existing Linux settings unchanged
- **WHEN** a Linux `settings.json` has `"unit": "llama-swap.service"`
- **THEN** the generated unit file path and the `systemctl` commands match those produced before this change

#### Scenario: Same settings on macOS
- **WHEN** the same `settings.json` is used on macOS
- **THEN** the service is managed as a launchd job whose label is derived from `llama-swap`

### Requirement: Installation writes a definition without activating it
`llms install-service` and `llms install-companions` SHALL write service
definitions without overwriting existing files. They SHALL NOT start, enable,
load or reload any service. They SHALL print the exact commands the operator
must run to make the service discoverable and to have it start at login.

#### Scenario: launchd install
- **WHEN** `llms install-service` runs on macOS
- **THEN** a launchd property list is written, no `launchctl` command is run, and the output shows how to load the job and how to make it start at login

#### Scenario: Existing definition
- **WHEN** the target definition file already exists
- **THEN** the command fails and the existing file is left unchanged

### Requirement: launchd job definition
A generated launchd job SHALL:
- run the same argument list the systemd unit would run;
- restart only after an abnormal exit;
- send stdout and stderr to a per-service log file under
  `~/Library/Logs/llms/`;
- set an explicit `PATH` taken from settings, so that engine binaries given by
  bare name resolve the same way they do in an interactive shell.

#### Scenario: Clean stop does not respawn
- **WHEN** a launchd-managed llama-swap is stopped with `llms stop`
- **THEN** it is not restarted by launchd

#### Scenario: Crash respawns
- **WHEN** the llama-swap process exits abnormally
- **THEN** launchd restarts it

### Requirement: Fail-closed service verification
Before starting, stopping, or restarting a service, and before any automatic API
operation that depends on it, the system SHALL verify that:
- the definition on disk is exactly what `llms` generates;
- the loaded service or job comes from that definition, with no overrides,
  drop-ins or transient state;
- the loaded program and arguments match the generated command;
- when the service is active, the live main process's executable and exact
  argument list match the generated command.

The live check SHALL work on Linux and on macOS. Any mismatch, or any state that
cannot be read, SHALL refuse the operation and change nothing.

#### Scenario: Modified definition refused
- **WHEN** the installed plist or unit file has been edited by hand
- **THEN** `llms start` fails with a "not the unmodified definition generated by llms" error and runs no service-manager action

#### Scenario: Live process mismatch on macOS
- **WHEN** the loaded launchd job's PID belongs to a process whose argument list differs from the generated command
- **THEN** the operation is refused with a live-process-binding error

#### Scenario: Unreadable process state
- **WHEN** the live process's arguments cannot be read
- **THEN** the operation is refused with a "cannot verify" error

### Requirement: Service lifecycle commands
`llms start`, `llms stop` and `llms restart`, and the companion equivalents,
SHALL perform the action through the selected service manager after
verification. `start` and `restart` SHALL wait until the llama-swap API is
ready, as they do today.

#### Scenario: Restart under launchd
- **WHEN** `llms restart` runs against a verified active launchd job
- **THEN** the job's process is replaced, and the command returns after `/running` and `/v1/models` answer

### Requirement: Service logs
The system SHALL provide `llms logs [--follow] [--companion NAME]`, which shows
the service's recent output. On systemd it SHALL read the user journal for the
unit. On launchd it SHALL read the job's log file.

#### Scenario: Follow logs on macOS
- **WHEN** `llms logs --follow` runs on macOS
- **THEN** new lines appended to the llama-swap log file are streamed until interrupted

### Requirement: Doctor reports the service manager
`llms doctor` SHALL report the selected service manager and whether its control
tool is available. Under launchd, it SHALL warn about any engine or companion
binary given by bare name that does not resolve on the configured `PATH`.

#### Scenario: Bare engine name not on launchd PATH
- **WHEN** an engine's `server` is `llama-server` and the configured launchd `PATH` does not contain it
- **THEN** doctor reports a failing check for that engine and names the `PATH` used
